# 2.1.1 Selection of Problem and Requirements Engineering for ML

**Problem selection.** Modern text-to-image generators (Stable Diffusion, DALL-E, MidJourney, …) produce photorealistic images at scale, fuelling misinformation, fake reviews, and trust problems for platforms and media. Reliably telling a **real photograph** from an **AI-generated image** cannot be solved with hand-written rules — the cues are subtle, generator-specific, and evolving — which makes it a genuine machine-learning problem.

**ML goal.** Build, deploy, and operate an ML component that, given an input image, decides whether it is real or AI-generated, exposed as a monitored production service. Our main task is binary image classification (real vs `ai_generated`), and optionally we might as well classify AI-generated images among the 5 generators (which generator model owns the image). Our focus is mostly on engineering around the model (reproducibility, QA, deployment, monitoring), not maximizing raw accuracy.

**What makes it unique.** Unlike a one-shot classifier trained on a single, dated generator, our component targets five recent generators (2022–2024) on realistic imagery.

**Intended use.** As the main use case of our ML component we can mention reliable platforms (such as news, social media, …) to distinguish real from fake (or generated) images to prevent misinformation and correctly flag likely AI-generated uploads via an API; another use case could be to quickly check the authenticity of an image with a confidence score, which is a well-documented and reproducible component for downstream developers to integrate in a larger system.

## 3. ML component specification (I/O contract)

- **Input:** one image (JPEG/PNG/WEBP), bounded file size; preprocessed identically to training (fixed square resize + uniform re-encode).
- **Output:** JSON `{"label": "real" | "ai_generated", "score": <float 0–1>}`; optionally generator model as well.
- **Operating context:** stateless REST service, containerised, with health and metrics endpoints.

## 4. Requirements

*Priority:* **M** = Must, **S** = Should, **C** = Could.

### 4.1 Functional (FR)

| ID | Requirement | Pri |
|---|---|---|
| FR-1 | Classify a single image as `real` / `ai_generated` | M |
| FR-2 | Return a confidence score in [0,1] with each prediction | M |
| FR-3 | Expose prediction via a REST endpoint (`POST /predict`) returning JSON | M |
| FR-4 | Accept JPEG/PNG/WEBP within a size limit; reject invalid input with a clear error | M |
| FR-5 | Apply the **same** preprocessing at train and serve time (resize + re-encode) | M |
| FR-6 | Provide health/readiness and metrics endpoints | S |
| FR-7 | Optionally return the most-likely generator (attribution) | C |

### 4.2 Data (DR)

| ID | Requirement | Pri |
|---|---|---|
| DR-1 | Use labelled real & AI images from multiple recent generators | M |
| DR-2 | Data & train/validation/test splits to be versioned and reproducible (DVC) | M |
| DR-3 | Handle class imbalance if observed in the data (via class weights or generator-balanced sampling) | M |
| DR-4 | Make sure no leakage such as image caption shared across train/val/test sets | M |
| DR-5 | Preprocessing to neutralise data to ensure the model does not rely on non-semantic **shortcuts** (such as aspect ratio, format) | M |
| DR-6 | Data usage complies with licence (CC BY 4.0 + MS COCO attribution) | M |
| DR-7 | Reserve a held-out generator (and data records) for drift evaluation | C |
| DR-8 | Automated data-quality checks (schema, class values, missingness, …) | S |

### 4.3 Model / performance (MR) — *targets (confirm, CI/CD?)*

| ID | Requirement | Target |
|---|---|---|
| MR-1 | In-distribution (similar test data) **balanced** accuracy | ≥ 0.85 |
| MR-2 | Macro-F1 and recall on **minority** class (usually real images) | ≥ 0.85 / ≥ 0.80 |
| MR-3 | **PR-AUC** | ≥ 0.90 |
| MR-4 | **Cross-generator** (leave-one-generator-out) balanced accuracy | ≥ 0.70 |
| MR-5 | Decision threshold based on validation results (not fixed 0.5) | — |
| MR-6 | Model retraining is reproducible (fixed seeds, versions, tracked data) | — |

Rationale: accuracy alone is misleading if there is class imbalance in data, so success is defined on balanced/minority-aware metrics and on generalisation to unseen generators.

### 4.4 Quality / non-functional (QR)

| ID | Attribute | Requirement |
|---|---|---|
| QR-1 | Performance | p95 inference latency ≤ 1 s/image on CPU *(confirm)* |
| QR-2 | Scalability | Stateless, containerised, handles concurrent requests |
| QR-3 | Reproducibility | One-command data pull + train; deterministic given seed |
| QR-4 | Maintainability | Passes static analysis (Pylint/flake8) + notebook lint (Pynblint); unit-tested (Pytest) |
| QR-5 | Energy efficiency | Training energy/CO₂ tracked (CodeCarbon) |
| QR-6 | Observability | Resource metrics (Prometheus/Grafana) + **data/model drift** detection (Alibi Detect) |
| QR-7 | Reliability | Health checks; graceful handling of bad input; best-effort uptime on free infra |
| QR-8 | Security/Privacy | Validate inputs; do not persist user images beyond the request by default |
| QR-9 | Portability | Reproducible Docker image on the chosen platform |
| QR-10 | Ethics/Transparency | Document dataset scope, biases, out-of-scope uses (dataset/model cards) |

### 4.5 Constraints & assumptions (CR)

| ID | Constraint / assumption |
|---|---|
| CR-1 | Compute limited to team laptops (Apple M4, 16 GB) + free-tier cloud → favours transfer learning on a small model |
| CR-2 | DVC remote is free-tier (~15 GB) → dataset must fit (**Defactify ~7.5 GB** ✓) |
| CR-3 | Licence: CC BY 4.0, **non-commercial academic** use, attribute paper + MS COCO |
| CR-4 | Scope is an ML **component (API)**, not a full end-user product/UI |
| CR-5 | Assumption: inputs resemble the training distribution (everyday photos vs full AI images), not face-swap/inpainting or adversarial inputs |

## 5. Success criteria (Definition of Done)

The component is successful when: it is **served via a reproducible, containerised API** (FR-1–5, QR-2/9); it meets the **model targets** MR-1–4 on a **leakage-free** test set (DR-4) with **shortcuts controlled** (DR-5); it is **reproducible** (QR-3, MR-6) and **monitored for drift** (QR-6, DR-7); and all choices, limitations, and metrics are **documented** in the dataset/model cards and report (QR-10). *(Numeric targets in §4.3 to be confirmed.)*

## 6. Risks & mitigations

| Risk | Mitigation |
|---|---|
| **Shortcut learning** (keys on square shape / format, not "AI-ness") | Normalise size + re-encode uniformly (DR-5); audited in EDA; report cross-generator metrics |
| **Class imbalance (5:1)** biases predictions | Class weights / generator-stratified balanced sampling; balanced metrics (DR-3, MR-1/2) |
| **Split leakage** (shared captions found in EDA) inflates scores | Caption-grouped re-split before training (DR-4) |
| **Generator drift** — fails on new generators | Leave-one-generator-out eval + drift monitoring (DR-7, MR-4, QR-6) |
| **Dataset scope/bias** (COCO scenes, 5 generators) | Document scope/limitations honestly (QR-10); keep out-of-scope explicit |
| **Compute/thermal limits** (passively-cooled laptop) | Transfer learning; offload heavy training to free GPU if needed (CR-1) |

Every requirement is owned by a milestone and has a verification method — the specification spans functional, data, model, quality, and operational concerns, which is what makes it *complete*.

## 8. Uniqueness & completeness statement

- **Unique:** a real-vs-AI detector trained and evaluated on **five recent generators** (not a single dated one), on **content-bias-controlled** data, and designed to be **operated and monitored** — with an explicit **cross-generator generalisation and drift** dimension rather than a train-once classifier.
- **Complete:** the requirements cover the whole ML-component lifecycle (data → model → API → packaging → monitoring), each requirement is **testable and traced to a milestone** (§7), and scope, constraints, risks, and out-of-scope uses are stated explicitly.
